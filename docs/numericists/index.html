The Sowel Method

Nine months. 303,000 lines of code in 41 repositories, running in a real house. Every line written by an AI, directed by one person. Eleven rules to stay in control.

Before we start

Any agent, same method

The examples come from Claude Code. Other coding agents work the same way: GitHub Copilot, Cursor, Codex and the rest.

They all read an instruction file when they start. They all follow procedures written in files. They all run commands and read the result. Only the file names change. Everything in this deck is plain files in the repository and checks in the CI, so it works with any of them.

The one idea everything follows from

Keep control, and make it last.

Building software with an AI has become easy. The real challenge is to stay in control, and to keep the project working for years.

You decide what. The agent handles how. You cannot read all its code, so you make it checkable: a spec you approve before, automatic checks after.

Under the hoodAn agent is a model with tools, in a loop. It reads files, runs a command, reads the result and tries again. That loop is why checks work: every check you write, the agent runs on itself before you see anything.

Act 1·rules 01 and 02

Set up

Once per project. The agent learns where it is, and how you work.

Rule 01

One file the agent reads first, every session

The agent has no memory. Each session starts from zero.

So one file tells it the essentials: where things are, which rules are not negotiable, what not to touch. It points to the rest. It does not explain everything.

Write down what a textbook would get wrong here: SI and not CGS, flux positive outward, which validation cases must still pass.

For a numericistWrite it once, or explain it again every morning for the rest of the project.

CLAUDE.mdexcerpt · 283 lines

### Logging

164 lines on day one, 283 today. A line is added after each real problem. In October the file was trimmed from 396 lines so it stays short.
Under the hoodEvery agent loads a file like this when it starts. It takes room in the agent's working memory, its context. A long file leaves less room to think. Keep it short, and point to the rest.

Rule 02

Your workflow is written down as skills

A skill is a procedure written in a file. It lists the steps in order. Each step ends with a gate: a checklist the agent must pass before going on. Some gates wait for your “ok”.

Sowel runs on four skills: build a feature, handle an issue, fix a bug, cut a release. Every software project has these four loops, and they share most of their steps.

You start a skill with one word. It runs the same way every time, even on a tired day.

For a numericistLike a post-processing script: written once, run every time, instead of redoing the figures by hand.

.claude/skills/4 loops · 3 helpers
feature  understand → spec ✋ → build + tests
         → check → agent review → merge ✋
issue    qualify ✋ → rewrite ✋ → route ✋
         → build → agent review → merge ✋ → close
debug    symptom → logs → root cause → diagnosis ✋
         → fix + check → merge ✋
release  pre-flight → release notes → merge ✋
         → tag → watch CI → verify

── helpers for this project ────────────────
plugin-dev · recipe-dev · docs
── ✋ waits for your “ok” ────────────────────
$ /sowel-issue 1210
Why gates matter. Without them, the agent does every step at once and says “done”. The gates make it stop where you need to look.
Under the hoodA skill is a Markdown file. The agent only sees its name and a short description until you call it. Then the full procedure loads. Some skills, like release, can only be started by you.

Act 2·rules 03 to 06

Frame the work

Before the code. This is where you keep control.

Rule 03

Start from the goal, then challenge what the agent proposes

Do not ask for a solution. Give the goal and the constraints, and let the agent propose.

Then challenge it. What does this cost? What breaks? Why not the other way? The design comes out of that discussion.

You used to pick the option you could afford to code. Now trying an option costs little, so you choose on merit.

The choice goes into the spec, with the rejected options and why. Otherwise the debate comes back in three months.

For a numericistLike defending a method choice in front of a reviewer, except that you are the reviewer.

Four options, three rejected in writing. The design that won is not one anybody would have written down at the start.
Under the hoodThe agent can go through the whole project in seconds, and never gets tired of arguing. You bring what it cannot know: what matters here.

Rule 04

Split the goal into small features, before any spec

Once the goal is clear, cut it into a sequence of small features. Each one is specified, built and checked on its own, and adds something that works.

The order follows the goal. Each feature moves the project toward it. Small steps with no direction just wander.

Then each feature goes through the same loop: spec, tests, code, review, merge.

Two warning signsIf you dread opening the result, the feature was too big. If you cannot say what it moves you toward, it is drift.

Under the hoodA feature is what fits in one conversation. In a long conversation the agent summarises older messages and loses detail. Hence the rule: one feature per conversation. A new idea becomes an issue for later.

Rule 05

Approve the spec before any code

Each feature starts with a short spec: what it does, how, and how it will be tested. The agent writes it.

You approve it before any code. Usually on a summary; you read the full spec when you need to. For a screen, you decide on mock-ups first.

A misunderstanding costs ten minutes on a page of text. Found in two thousand lines of code, it costs half a day.

For a numericistApprove the derivation, not the loop. It is the only review you can still do at this speed.

Under the hoodThe agent forgets between sessions; the project remembers, in three places. The code says what the system is, the docs what it does, the spec why it was built that way. A new session reads them and picks up the thread.

Rule 06

Decide the tests before the code

The spec includes a test plan: the normal cases, the edge cases, and what must not change.

A test written after the code only records what the code does, mistakes included. An AI will happily write a passing test over wrong code.

For a numericistYou choose the analytical case before meshing, not after looking at the curve.

Act 3·rules 07 to 11

Lock in

What keeps the project working after six months.

Rule 07

You make the decisions; another agent reviews the code

Reading all the code would take 1,010 hours. Nobody can. So your attention goes to decisions: the goal, the spec, the merge.

The line-by-line review goes to a second agent. It did not write the code, so it has nothing to defend.

You decide what goes in. Since Opus 5.5, I sometimes let the agent merge on its own. That is a choice made for a task, never the default.

For a numericistPeer review plus conservation checks. Both, not one or the other.

what the review agent checksevery change
Correctness  logic bugs, empty or offline cases,
             the edge cases listed in the spec
Conventions  the rules in CLAUDE.md
Scope        the change does only what the spec says
Tests        every planned scenario has its test
Security     no leak, no weakened protection

Each finding: a file:line and a concrete failure.
The default, in CLAUDE.md: “Never merge a PR without explicit user approval.”
Under the hoodThe reviewer is a separate agent with a fresh context. It sees the change and the rules, not the reasoning behind them. It has no tool to edit files: it reports, and the first agent fixes.

Rule 08

Everything the machine can check, it checks

An agent says “it works” with the same confidence whether it works or not. Only a check gives a real answer.

So the CI checks everything it can: format, lint, types, static analysis, secrets, tests, docs, specs. Each check is an answer nobody can argue with.

In the backend there is almost one line of test per line of code: 54,277 of code, 53,140 of test.

For a numericistThe manufactured solution. You do not validate a solver by checking that the output looks about right.

Under the hoodThe agent runs the checks itself, reads the errors and fixes them before showing you anything. Every check you add is one more thing the agent corrects on its own.

Rule 09

Docs ship with the code: one guide for users, one for developers

The docs are written in the same change as the code, by the agent. A change without its docs is not finished, and the CI checks it.

Two guides that never mix. The user guide explains tasks, without jargon. The technical guide gives the architecture, the API and code examples.

72 pages in two languages used to be out of reach. With an agent it is routine. And reading the docs back finds bugs.

The real payoffDocumentation was always the first thing cut. It is now the cheapest part of a change.

Rule 10

A rule only holds if a check enforces it

Writing a rule down is not enough. Even in the file the agent reads every session, it fades after a few months.

A rule holds when breaking it makes a check fail, automatically, with nobody having to remember.

So every incident takes the same path: a rule in the file, then a check. A real one on the right: an import that compiled, passed the linter and every test, then refused to start in production.

For a numericistAn assertion in the code beats a remark in the report.

Under the hoodThe check's message is written for the agent. When it fails, the agent reads why and fixes the cause on its own. Write error messages like instructions.

Rule 11

Use the agent to improve how you work

Do with your process what you do with your product. Give the agent a goal: “find where the docs drift from the code”.

Then discuss what it finds, and how to fix it, like any other change. In August it found three months of drift, proposed the checks, wrote them and added them to the CI.

Nothing in this deck existed on day one. Everything came out of this loop.

Why it compoundsEvery hour spent on the process pays back on every change after it.

Avoid·all of these happened

Four traps

  • Asking for everything at once. “Build me the solver” returns a lot of code you cannot check. You can only take it or leave it.
  • Believing “it works”. The agent says it with the same confidence when it is false. Ask for the command it ran and its output.
  • Letting the scope drift. The agent will happily “improve” three other files on the way. What you did not ask for is not checked.
  • Loosening a check to get a change through. That is exactly when drift starts again. Fix the cause, never the check.

Getting started·in this order

What to do on Monday

  1. An instruction file, one page.What the project does, where things are, the rules that are not negotiable. It will grow with each problem.
  2. One command that says yes or no.Build, format, tests: one command, one verdict. Every other rule depends on it.
  3. Your feature workflow, as a skill.The steps in order, a gate after each one, and your “ok” before the code and before the merge.
  4. Give the goal, argue, then approve a spec.On something you know well, so you can judge. Then measure the time saved while building.
  5. One automatic check, on your weak point.Pick what always drifts in your work, and make it fail the build. Just one, to start.
  6. After each incident, a rule and a check.Repeated for nine months, that loop built everything in this deck.
