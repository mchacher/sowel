The same arithmetic explains why I cannot simply check it all myself: at the conservative end of the review range, 200 lines an hour, reading this code once takes 7.2 months of full-time work — longer than it took to produce. Rules of thumb, not measurements: 50–100 lines of production code per person-day sustained, and 200–400 lines per hour of effective review before comprehension collapses. Halve them or double them — the conclusion does not move. And this counts code only: the 82,000 lines of specifications and documentation are on top.

The one idea everything else follows from

You do not read the AI's code. You make the AI's code checkable.

An AI produces more code in an hour than you can read in a day. If quality depends on your reading, you are the bottleneck, and you will give up inside a fortnight.

So the human effort moves upstream, into the specification, and downstream, into automated checks. Almost nothing is left in the middle.

Act 1·rules 01 to 04

Frame

Before the first line of code. The highest-return phase, and the one everybody skips.

Rule 01

One entry document, re-read every session

The agent has no memory between sessions. Everything it must know lives in a single file it reads at startup.

That file does not describe the code. It points: where to look, which conventions are not up for discussion, what must not be touched.

On an existing codebase the payoff is immediate. Write down which HTTP client you actually use, that timestamps are UTC at every boundary, which module nobody touches without asking, and the two patterns the team has already rejected. An agent that has not been told will write perfectly idiomatic code that belongs in somebody else's repository.

For a developerIt is the onboarding document you never wrote — except this new hire reads it every single morning.

Rule 02

Use it to widen the option space, then choose

The instinct is to ask for a solution. That wastes the machine. Ask instead for four ways to do this, and what each one fails at — then decide yourself.

For a working team this is where the job changes. Implementation cost used to settle architectural arguments by default — you shipped the option you could afford to build. A design you dismissed because it meant rewriting the persistence layer is now a branch you throw away on Thursday, so the shortlist stops being set by what you can afford to write.

The best place to practise the habit is on your own checks, because a badly designed gate is worse than none. “The docs keep drifting, add a check” gets you the first idea the model had. The question on the right got a design.

Whatever you choose goes in the spec. So do the rejected options, with their reason — otherwise the same argument reopens in three months and nobody remembers why it was settled.

For a developerYou already know three ways to do most things. The value is the fourth one, and being told what each costs before you commit.

Rule 03

Write the spec before the code, and approve it explicitly

Every feature starts as a folder of three documents. The AI writes them. The human reads, corrects, approves. Nothing starts without agreement on those three pages.

This is where the whole method earns its keep. A misunderstanding costs ten minutes on two pages of prose. The same misunderstanding found inside two thousand lines of code costs half a day — and you will be tempted to keep the code rather than throw it away.

And the specification is not only yours to write. Have it lay out the data model, the event flow, the API contract and the failure modes — then argue with it. What you approve is two pages of design, which you can genuinely review, rather than a diff, which at this volume nobody can.

For a developerIt is an architecture decision record that arrives before the code instead of six months after it.

Rule 04

The test plan is written before the implementation

A dedicated section of plan.md lists the nominal cases, the edge cases, and what must not change. Written before the first line, approved with the spec.

A test written afterwards only records what the code already does, mistakes included. With an AI the gap is stark: it will happily write you a passing test over wrong code.

For a developerTest-driven development with the part nobody does: writing down what you intend to prove, before anything can prove itself right.

Act 2·rules 05 to 07

Produce

During the work. Speed is a given. What is at stake is size and order.

Rule 05

Increments you can throw away, a direction you cannot

A wide request — “build me the engine” — returns a great deal of plausible, uncheckable code. Your only options are to accept it whole or lose all of it. The right size is what you read in one sitting and discard without pain if it went wrong.

But small steps with no bearing simply wander, and 726 locally sensible decisions make an incoherent product. Every increment is measured against a destination written down in advance — the architecture, the roadmap, and above all a one-line invariant that has arbitrated hundreds of decisions since month one.

When a proposal does not serve that line it is dropped, however good it looks on its own. In practice: one spec, one branch, one batch, one day — each one a step towards the stated end state, not merely a step.

Two warning signsIf you are not looking forward to opening the result, it is too big. If you cannot say what it moves you towards, it is drift.

Rule 06

Explicit gates, not good intentions

The method is itself a document the agent must follow: understand, specify, implement, validate, get reviewed, document, wait for approval. Seven steps, seven blocking gates.

Without them an agent collapses the seven steps into one and hands you the lot marked “done”. It is not cheating. It is optimising for giving you a result, and nobody told it where to stop.

For a developerA definition of done the machine can read. Yours lives in a wiki page nobody has opened since the offsite.

Rule 07

Freeze the procedures you repeat

Seven procedures come up again and again. Each is written once, named, and invoked with a single word. You never re-explain how you work.

The gain is not typing time. It is that the procedure does not degrade on a tired day, and that it improves cumulatively instead of being reinvented each session.

For a developerThe runbook you always meant to write — except this one is executed, not read.

Act 3·rules 08 to 12

Lock in

What survives six months. The part everybody underestimates, and the only thing separating a prototype from a living project.

Rule 08

Spend your attention on decisions, not on lines

Human attention is the scarce resource — 723 hours to read this code once. It is spent on the spec and the architecture, where a mistake propagates everywhere. Not on line-by-line review, which goes to a second agent that did not write the code and has no stake in liking it.

One decision is never delegated: nothing enters the main branch without explicit human approval. That is the last line of defence, and it has never been automated.

For a developerThis is the one that stings. Reading the diff was the job. The job is now choosing what gets built, and keeping the merge button.

Rule 09

One line of test for every two of source

73,000 lines of test against 144,000 of source. In the backend, where the logic actually lives, it is very nearly one to one: 42,312 lines of source, 41,058 of test. The AI writes both — and that is exactly why you need that many.

An agent will tell you something works with total confidence whether it does or not. A suite that runs in three minutes is the only contradictory answer that costs nothing to replay, and the only one still valid in six months when nobody remembers the context.

For a developerYou already believe this. What changes is that writing them is no longer the reason you skip them.

Rule 10

Documentation is a deliverable, in two registers

It is written in the same batch as the code, by the same AI, and reviewed like everything else. Crucially it is split into two registers that never mix: a user guide, task-oriented and jargon-free, and a technical guide with signatures and examples.

This is where an AI is most spectacularly worth having. Writing 70 coherent pages in two languages stops being a trade-off and becomes a reflex.

The real payoffDocumentation was always the first thing cut. It is now the cheapest item in the batch — and reading it back finds bugs.

Rule 11

The rule lives in the document, the guarantee lives in the machine

This is the most expensive lesson of the project. Writing a rule down — even in the document the agent re-reads every single session — is not enough to make it hold for six months.

Violating it has to break something visible, automatically, with no human remembering anything. A rule with no check attached is an intention. The next view proves it.

For a developerA lint rule beats a style guide. A failing build beats a comment on a pull request.

Rule 12

Every incident becomes a rule, then a check

A real one: a file extension left off an import. It compiles, it passes the linter, it passes all 235 test files — and it refuses to start in production.

The fix was not “be careful next time”. A sentence in the framing document, plus an automated check that now rejects the case, with a message explaining why.

For a developerA post-mortem that ends in an action item is a story. One that ends in a failing check is a fix.

Rule 13·rule 02, pointed inwards

Turn it on your own process, not just your product

The same widening works on the toolchain, and this is where it compounds. Ask it to audit how you work, propose three ways to fix what it found, and then build the one you pick.

The August documentation audit is the clearest case. The AI was asked to go and find drift. It found three months of it, proposed the gates, wrote the spec, wrote the scripts, and wired them into CI. Two jobs became five.

Nothing in this deck was in the project on day one. All of it came out of that loop, and the loop keeps running.

The compounding partEvery hour spent on the process is repaid by every batch after it. Nothing else in the method compounds like this.

Avoid·all of these were lived

Six traps

  • Reviewing the diff out of reflex. It feels like diligence. At 1,500 lines a day it is theatre — you are sampling, not reviewing, and the sampling is what makes you feel covered.
  • Asking wide. “Build me the app” returns something impressive, plausible and uncheckable. You will only be able to take it or leave it whole.
  • Believing “it works”. An AI says it with identical confidence whether it is true or false. Ask for the command it ran and the output, never the conclusion alone.
  • Letting scope drift. An agent will gladly “improve” three neighbouring files on the way past. What you did not ask for is not reviewed, so it is not checked.
  • Re-explaining the same convention every session. If you have said it twice, it is not in the framing document. Write it once and stop repeating it.
  • Loosening a check to unblock a batch. That is the exact moment drift restarts. Fix the cause, never the barrier.

Getting started·in this order

What to do on Monday

  1. A framing document, one page.What the project does, how it is laid out, the conventions that are not negotiable. One page is enough — it will grow on its own, by incident.
  2. One command that says yes or no.Build, tests, formatting: a single command, a single verdict. Without it none of the later rules has anything to grip.
  3. Ask for three options before the first spec.On something you already know well, so you can judge the answer. This is the habit that turns the AI from a typist into a colleague.
  4. The first spec, approved before any code.Have it written, correct it, then measure the time saved during implementation. That is what will convince you, not this deck.
  5. One automated check, on your known weak point.Pick the thing that always drifts in your work. Make violating it fail the build. Exactly one, to start.
  6. After every incident, one more line.A rule in the document, a check in the machine. That cycle, repeated for seven months, built everything else here.

You do not read the AI's code. You make the AI's code checkable.

Everything else — the thirteen rules, the six artefacts, the five checks — is only the implementation of that sentence.
